\chapter{Prototype and Experimental Environment}
\label{ch:experimental-environment}

This chapter documents the prototype implementation and experimental environment used to evaluate the Wolverine intelligence platform. It defines the experimental objectives, details the containerized deployment environment across its three network domains, formalizes the deterministic synthetic data generation pipeline, characterizes the experimental dataset, establishes the reproducibility protocol, and analyzes runtime resource boundaries.

\section{Experimental Objectives}
\label{sec:exp-objectives}
The experimental prototype is designed to evaluate specific research and engineering questions within a strictly bounded testbed:
\begin{enumerate}
    \item \textbf{Architectural Validation:} Demonstrating the feasibility of isolating an untrusted multi-stack synthetic ecosystem from an intelligence analysis pipeline on a single host.
    \item \textbf{Deterministic Synthetic Generation:} Evaluating whether a 13-phase procedural generation engine can synthesize realistic, multi-site relational ecosystems with controlled alias mutations and verifiable ground truth.
    \item \textbf{Pipeline Integration:} Verifying that heterogeneous payload formats (REST, JSON:API, GraphQL, HTML) can be normalized into unified Canonical Records with cryptographic provenance tracking.
    \item \textbf{Algorithmic Proof-of-Concept:} Assessing the execution of heuristic Jaro-Winkler entity resolution and in-memory graph traversals under explicit memory and computational bounds.
    \item \textbf{Prompt Safety Demonstration:} Verifying the efficacy of 4-rule input sanitization and deterministic fallback heuristics when language models ingest untrusted context.
\end{enumerate}
The prototype is explicitly categorized as an experimental research testbed rather than a production deployment.

\section{Environment and Container Infrastructure}
\label{sec:exp-environment}
The prototype executes on a single workstation host containerized via Docker and Docker Compose. The topology isolates 14 services across three distinct Linux bridge networks:

\begin{itemize}
    \item \textbf{\texttt{wolverine-dmz}:} Handles external ingress. Houses the Nginx Tor gateway bridge (\texttt{tor-gateway}) and the frontend presentation container (\texttt{analyst-ui}).
    \item \textbf{\texttt{wolverine-internal}:} The primary service mesh. Interconnects the five synthetic applications (Atlas, Briar, Cinder, Drift, Ember), application databases (\texttt{postgres-sites}, \texttt{mysql-site-c}), cache (\texttt{redis}), capture storage (\texttt{minio}), and the analytical backend (\texttt{wolverine-api}).
    \item \textbf{\texttt{wolverine-truth}:} The isolated evaluation network. Configured with \texttt{internal: true}, this bridge has no default gateway, strictly isolating the Truth Vault (\texttt{postgres-truth}) from all application containers and external networks.
\end{itemize}

\section{Synthetic Data Generation Engine}
\label{sec:exp-synthetic-generation}
Because real-world underground intelligence data contains sensitive PII and lacks verifiable ground truth, Wolverine implements a procedural generation engine (\texttt{generator/src/generator/engine.py}).

\subsection{Seed Control and Determinism}
The generator initializes a pseudorandom number generator using a fixed master seed ($S_0 = 42$). Every entity, alias mutation, listing, message, and transaction timestamp is deterministically derived from $S_0$, ensuring identical dataset generation across independent runs.

\subsection{13-Phase Generation Pipeline}
The generation engine executes sequentially across thirteen deterministic phases:
\begin{enumerate}
    \item \textbf{Canonical Person Synthesis:} Generates $N = 50{,}000$ base personas with canonical demographic metadata.
    \item \textbf{Cross-Site Account Distribution:} Assigns accounts across platforms following an empirical distribution (50\% on 1 site, 30\% on 2 sites, 14\% on 3 sites, 6\% on 4--5 sites).
    \item \textbf{Handle Mutation Injection:} Applies an alias mutation model with a 35\% probability per secondary account (prefixing, suffixing, character drops, dot/dash substitutions).
    \item \textbf{Marketplace Listing Generation:} Creates product listings across Atlas, Briar, and Ember.
    \item \textbf{Escrow Order Lifecycle Simulation:} Synthesizes multi-stage transactions advancing through 7 discrete states.
    \item \textbf{Private Messaging Synthesis:} Generates conversational threads between cross-site buyer and seller personas.
    \item \textbf{Forum Thread and Reply Synthesis:} Populates Drift Forum with hierarchical categories, threads, and timestamped replies.
    \item \textbf{Reputation Event Generation:} Assigns feedback scores and review logs.
    \item \textbf{Interaction Graph Edge Synthesis:} Creates inter-entity relationships.
    \item \textbf{Support and Notification Events:} Generates ticket logs.
    \item \textbf{Controlled Noise Injection:} Injects 3--8\% randomized noise links into the evaluation dataset.
    \item \textbf{Scenario Overlays:} Injects structured investigative scenarios (\texttt{alias-bridge}, \texttt{reputation-ring}, \texttt{migration-noise}).
    \item \textbf{Referential and Prohibited Content Validation:} Validates database foreign keys and verifies zero occurrences of prohibited terms (e.g., real cryptocurrency keys or genuine credit card patterns).
\end{enumerate}

\section{Reproducibility Protocol}
\label{sec:exp-reproducibility}
Full replication of the experimental setup requires Docker 24+, Docker Compose v2, Python 3.10+, and Node.js 20+. The execution sequence is:
\begin{enumerate}
    \item \textbf{Infrastructure Initialization:} \texttt{docker-compose up -d} provisions the 14 containers and attaches networks.
    \item \textbf{Deterministic Database Seeding:} \texttt{python -m generator --seed 42 --persons 50000} seeds source databases and populates the Truth Vault.
    \item \textbf{Ingestion and Normalization Execution:} The collection daemon executes HTTP queries via \texttt{tor-gateway} and populates MinIO and WolverineDB.
    \item \textbf{Resolution and Graph Verification:} The entity resolver executes blocking and scoring, projecting edges into \texttt{GraphProjector}.
\end{enumerate}

\section{Runtime and Resource Boundaries}
\label{sec:exp-resource-boundaries}
The single-host experimental deployment operates under explicit resource bounds:
\begin{itemize}
    \item \textbf{Memory Footprint:} Bounded to 16\,GB host RAM. The in-memory graph projector caps active traversal depth at $d \le 4$ and maximum projected nodes at 500 per query.
    \item \textbf{Storage Consumption:} The complete synthetic database image, MinIO capture bucket, and PostgreSQL volumes require approximately 4.2\,GB of disk storage.
\end{itemize}
These bounds confirm that the platform is engineered for single-host demonstration and controlled research rather than distributed big-data scaling.
